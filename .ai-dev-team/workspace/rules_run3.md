# Rule list — run 3 (FR-17..FR-21)

Copied from ai-dev-team rule-packs.md §3 (BASE) and resource-budget.md §7 (COST). Report per rule-packs.md §6 (developer) / §7 (verifier).

## 3. `BASE` — rules for every task
1. **Scope** — only the task's files and behavior change; unrelated problems are written in the notes, not fixed.
2. **Contracts** — request/response shapes, types, nullability and error codes match the design exactly; a wrong contract is reported `BLOCKED`, not changed.
3. **Tests first** — each acceptance behavior the task touches has a test that was seen failing before the code existed, or the notes say why a test is impractical and how it was verified instead.
4. **Evidence** — the notes hold the trimmed real output of the final related-test, lint and type-check/build runs.
5. **Heavy commands** — test runs, builds and e2e went through `$TEAM_BIN/run-heavy.sh`; no watcher, dev server, emulator or browser is left running.
6. **Language** — code, comments, specs and notes are in English; comments explain why and never describe bug history.
7. **Commits** — none unless the user asked; messages are English and imperative; AI attribution (a `Co-Authored-By: Claude …` trailer, "Generated with Claude Code", 🤖) in commits and pull request descriptions follows the project's policy — its `CLAUDE.md` or `.claude/settings.json` `attribution` first, the user's global instructions otherwise; one commit per task, adding only the task's files and named team files (never `git add -A` or a whole folder), checked with `rule-checks.sh staged-media`; a fix round or quick pass is committed only after its re-check passed (the task's reviewer, and its qc when a `QC_FAIL` opened the round).
8. **Dependencies** — no new dependency without a stated reason (maintained, size/cost acceptable, no existing utility does it); a new dependency or version was published at least 14 days before it was added, unless the user approved a newer one — the exact version named in a plan the user approved counts as approved (supply-chain attacks are usually caught within days).
9. **Security defaults** — input validated at the boundary, parameterized queries, an authorization check on every entry point, no secrets in code or logs.
10. **Test scope** — per task and per fix round only the related tests of the changed files and the mapped guards ran (no whole-suite or all-guards runs); failures outside the task are reported as `not mine`, not chased with reruns.
11. **Shared tree** — no `git stash`, `checkout`, `restore`, `reset`, branch switch, or moving / deleting tracked files on the working tree other agents share, except the files a removal task lists in its board row. The index belongs to the user's commit: until the user approved commits for this run, files are deleted with plain `rm` (never `git rm`, `git mv` or `git add`), so the deletions sit unstaged beside the other changes and the user stages them together; to show a test failing without the change, copy the file to `$TEAM_WS/` and copy it back, or write the test before the code. This holds in fix rounds and quick passes too; the index itself is covered by `BASE-24`.
12. **Other repositories** — nothing was written outside this repository unless the brief names that repository and its files and states the user approved it.
13. **Untracked files and shared environments** — no untracked file or directory was deleted without listing it and getting the user's yes (it cannot be restored from git), except files the team created in this run and recorded as created in a task's notes, which may be deleted and are listed in the report; before installing, uninstalling or resetting anything on an environment that mounts the repository (a container with the source bind-mounted, a CMS that deletes extension folders on uninstall), `git status` was taken, and taken again after — a tracked file that changed or vanished is restored and reported. Local secrets files (`.env`) change only by named keys, after a backup, and the notes list the keys changed.
14. **Waiting on your own command** — a test or build ran in the foreground through `run-heavy.sh` (it applies a timeout), or, when it may outlast the foreground limit, as a background task: the agent then ends its turn without a waiting loop, is resumed when the command finishes, and sends its report. No `sleep`/`until` loop, Monitor or second background task waits on the first, and no hand-back or report is sent while the command still runs (ending the turn is enough). A command that hangs or times out is reported as hung with the step that was running, not left running.
15. **Own processes only** — the agent stopped only background tasks it started, with `TaskStop <id>` (every long command runs as a background task, so there is no other process of its own to stop); never `pkill`, `killall` or `kill` by name or pattern, and never a command that stops shared daemons or stacks (`gradlew --stop`, `flutter daemon` shutdown, `docker compose down` / `stop` / `restart` of a stack others use), which also kills other agents' test runners and builds. A stray process it did not start is reported to the leader.
16. **Reuse first** — before adding a feature, component, service, helper, endpoint, script or fixture, the project's capability index (`$TEAM_STATE/capabilities.md`) and the plan's reuse notes were checked, then a bounded search by name; an existing fit was used or extended. The notes hold a `## Reuse` table: what was needed, where it was looked for, and `reused <path>`, `extended <path>` or `new — <why nothing fit>`; anything new that others can reuse is added to the index.
17. **Shared toolchains and data** — no SDK, toolchain or shared tool was installed or upgraded by the task (a missing or wrong version is reported to the leader, who installs it once), and nothing was written into `$TEAM_TOOLS`; scratch tests and probes that commit data outside a rolled-back transaction (forked processes, a second connection, calls to a running app) removed what they wrote, and the notes show the before/after count; committed tests that write shared data follow `BASE-27`.

18. **No sub-agents** — the agent did not start agents of its own (the Agent tool, Workflow); work that would go faster in parallel is reported to the leader, who splits it within the run's caps and models.
19. **Notes from the start** — the task notes file was created when the work began and gained a progress line after each step (read, red test, code, related tests, sweep, each qc flow checked with its result), so a replacement agent continues from it and the watchdog sees progress. Times in the notes come from `date`, never written from memory.
20. **Removal checks every reference** — before deleting code, strings, keys, routes, options or assets, usages were searched including dynamically built names (prefixes such as `LABEL_`, string interpolation, config and template files, other apps of the repo); what is still used stays, and the notes list what was searched.
21. **Secrets stay out of team files** — command output that holds a password, token, key or secret value was redacted before it was saved to `$TEAM_WS/`, `qa-artifacts/` or the notes (evidence is its length, a hash or the key name); a generated secret lives only in a shell variable that is unset after use; any file that held a secret was deleted when the task ended.
22. **Names follow their place** — a new name (secret key, environment variable, client id, table, column, route, config key) follows the convention already used by its neighbours in the same place (the same vault project, `.env` file, realm, schema); the notes give the name and the neighbours it was matched to. Different layers may keep different conventions; one value never gets two spellings within a layer.
23. **Every entry path** — a feature reachable in more than one way (an admin action run step by step and a CLI that runs the chain, a web and a mobile client, a first run and a re-run) has tests or qc evidence for each path; the notes list the paths.
24. **No index or history changes** — developers, reviewers and qc ran no command that changes the git index or history on the shared tree (`git add`, `git rm --cached`, `git reset`, `git restore --staged`, `git commit`, `git stash`); only the leader changes the index, at commit time. A task's diff comes from `$TEAM_BIN/rule-checks.sh task-diff`, which works on a copy of the index.
25. **Guard run before DONE** — the profile's `guard` command (fast guard / static tests and lint of the changed files, accessibility lint where the stack has one, and the meta tests that scan the source tree or docs) ran on the final code and passed; the notes hold its trimmed output. A substitute (a related test run, a lint of other paths, "guard not mapped for this app") is not a guard run: a missing mapping is reported to the leader, who adds it to the profile (`rule-checks.sh guard-coverage`) before the DONE gate accepts the task.
26. **Rewrite parity** — a task that re-implements a feature in another stack or framework covers every item of the plan's behaviour inventory of the old implementation (controls, states, errors and recovery paths, stored data and its keys); the notes map each item to the new code, and qc walked the list item by item.
27. **Isolated tests restore shared data** — a test that writes a shared database, demo site or stack (accounts, permissions, settings, seeded records, CSRF or other global switches) first checks it runs in the isolated test environment and skips otherwise, and restores everything it changed in `finally`, so a failing run leaves nothing behind; the reviewer checks every new or changed test that writes outside a rolled-back transaction.
28. **Third-party code last** — a change to code the project does not own (an open-source server or its extensions and SPIs, a fork of an upstream, another team's repository) was planned only after the plan listed, in order, a solution on this project's side, then configuration of that system (settings, realm, roles, flags), each with why it does not work; the user chose the code change explicitly.
29. **The user's signed-in browser** — the user's own browser session on a system outside this repository (an admin console, a shared dev or production site, a monitoring tool) was used only after the user said yes for that page and purpose, read only; requests, headers, cookies and storage of authentication endpoints were never read. Data the agent cannot see otherwise is asked from the user (a screenshot or pasted value).
30. **Checks clean up their data** — a browser or flow check that creates records on a shared app or demo (orders, bookings, accounts, uploads) removes or cancels them through the app's API in `finally` of the same script, or runs against the profile's QA records (`ui_seed`); the notes show the created ids and that they are gone. Clean-up deletes only those recorded ids (records, files, mails), never by a name prefix or pattern such as `test_*`, which also removes what other agents or the user created. State is never fixed with hand-written SQL, and a task never hands its leftovers to another task.
31. **Containers write as the user** — a command run in a container that writes into a bind-mounted path runs with `--user "$(id -u):$(id -g)"` or writes under `$TEAM_WS/qa-artifacts/`; `git status` after the run shows none of its files, and a root-owned file that cannot be removed is reported.
32. **Decisions honoured** — the diff keeps every decision the brief's `Decisions` line lists (spec `D…` entries, `decisions.md`); a change that contradicts one is `major` unless the user changed the decision.
33. **Target environment verified** — a change that relies on the state of another system (a role, scope, client, flag, deployed image or migration) names that assumption in the notes with how it was checked on the environment the user will use (admin API, version endpoint, log, image tag) or marks it `unverified on <env>`; a change across several repositories lists their deploy order, and after merge each repository's running version on the target environment is checked before the user is told to try it.
34. **Blocked step, next route** — a step stopped by the permission system or by the target (a bot wall, 401/403, a missing tool) is recorded in the notes as `BLOCKED-STEP: <step> — <reason>` and reported to the leader at once; the agent switches to an equivalent allowed route (another licensed source, an official API) without asking, never works around the block, and asks only when no allowed route exists. Sending the same call again after the permission system denied it is a workaround, also for the leader. An outward action the user asked for (push, pull request, tracker comment) that is denied goes to the user as the ready command or link with the denial reason; only a denial whose cause is plain in the call (a line the project's policy forbids) may be retried once with that cause removed, and the retry is reported to the user in the same message. Reaching the denied effect another way — another flag or wrapper (`git -C <dir>`, `xargs`, `find … | …`), a list file, or the same work split over two calls — counts as sending the denied call again.
35. **User rules** — every `USER-n` line of `$TEAM_STATE/user-rules.md` that applies to the task's screens or area holds, measured as the line says; a `USER-n` fail is `major`. When a `USER-n` line and a plugin rule cannot both hold on one element (a fixed row height and an uncut name), neither is loosened in a test on the agent's word: the leader records the conflict as a decision with both rules named and the options (a layout change that keeps both, or which one gives way), asks the user, or while away takes the option that keeps both when one exists and lists the decision first in the report; a test allowance that follows from it names the decision.
36. **App scope** — a task in an app adds nothing outside that app's scope in the profile's `apps` line (a booking flow in a POS-only app); a feature outside it is `major` unless the user widened the scope, and the profile line is updated when they do.
37. **Live repro for runtime defects** — a fix of a defect found on the running app (by qc, sign-off, Phase 5 or the user) replays the reporter's exact steps on a build that contains the change (same widths, theme, input: "click, then hover") and records in the notes that they fail before the fix and pass after; a unit, widget or golden test is added too, and it exercises the component the screen actually renders (found from the screen's code, not assumed from its name). A `DONE` backed only by a test of another component or of the theme goes back.
38. **Formatters on your own files** — formatters and auto-fixers (`dart format`, `prettier --write`, `eslint --fix`, `black`, `gofmt -w`, `php-cs-fixer`) ran only on the files the task changed, never on a directory or the whole tree; format problems found elsewhere go into the notes as out-of-scope.
39. **Schema upgrade path** — a task that changes the schema (a table, column, index or enum value in the install schema file or a migration) also ships the path that brings an existing install to it (the stack's migration or update script, run by the installer or `app_start`), and applies it to the shared demo through that path in the same task, with the before / after check in the notes; a schema that reaches an existing database only by importing the install file by hand is `major`.
40. **Outward writes as the user** — before a write to a system outside this repository (a tracker comment or issue, a pull request, a chat message), the identity of the connector or CLI that writes was checked (the tracker's `whoami`, `gh api user`) and matches the user; under another account nothing is posted — the text goes to the user with the step to reconnect. A message for readers who do not work on the code (QC, product, support) describes what they see and what to test, without endpoints, class names, file paths or error keys.
41. **No borrowed credentials** — no credential, token, cookie or session was read from a database, session store, browser profile or log to act as a user; sign-in uses the profile's `test_logins` (or a test persona / sign-in link the app accepts), and a role without one leaves the criterion `unverified` with a request for the user to sign in.
42. **Test settings for every runner** — a change to test parallelism, timeouts, retries or test-environment resources (workers, pool sizes, CPU/memory limits) states its value for every place that runs it — the local machine and each CI runner read from the CI files (`runs-on`, runner size) — and the service capacity it meets (server workers, connection pools); the task is done only after the CI run of the change passed. A setting that exceeds a runner's resources or is left unstated for one is `major`.
43. **Access fixes for everyone** — when an access rule does not hold (a role cannot do what the decision allows, or can do what it forbids), the options offered change it for everyone the rule covers (code, or configuration kept in the repository); granting a role or editing data for one account is never offered as a fix, only named as a temporary unblock when the user asks for one.
44. **Fakes walk the changed flow** — a client task that changes a flow on an app built on a fake or demo data adapter also makes that adapter able to run the flow end to end (the requests, the server's answers and the states the change shows), so qc walks it on the build; a criterion qc can check only in widget or unit tests is reported `unverified on the build` with the missing fake step, never `pass`.
45. **Criteria live in the spec** — every `AC-n` a brief names is in the spec file with the same text; a criterion added during the run (a user decision, a scope change, a fix's expected behaviour) is written into the spec with its `D…` entry before the brief that uses it, never only in a brief. A verifier judges against the spec, and a brief criterion missing from it is a `fail` of this rule.
46. **Evidence on the final code** — runtime evidence (a qc walk, a real run of a script or `make` target, a browser flow) names the commit or build id it ran on and was produced after the task's last change to runtime code; a fix round or quick pass that changes runtime code (not only tests, comments or docs) is run again for real on that code before the task is committed — a stub or unit test alone does not carry an earlier real run forward. `qa-artifacts/` holds logs, outputs and images, never copies of source files or docs, which go stale; evidence points to the file in the tree or the commit.
47. **Every reader of a fixed value** — a fix to how a value is computed or shown (a total, a rest, a status, a count, a date) lists in the notes, under `## Readers`, every place that reads that value — found by a search for the field, provider, getter or helper, across screens, sheets, bars, prints, exports and fakes — with `fixed`, `already right` or `not affected — <why>` per row; the reviewer checks the list against its own search, and a reader left out that still shows the old value is `major`.
48. **State read back, not assumed** — a report that something on a real machine or account is in a state (an option selected, a service running, a package installed or removed, a setting applied, a source current) quotes the command that read it after the change and its output; a script's own progress lines, its exit code or the intended result are not evidence of the state, and a desktop or system integration task is not called done on a virtual session alone while a real-machine check is still open — the report lists it as `not verified on the real machine`.

## 7. `COST` checks
1. **Heavy commands** — test suites, builds, e2e, audits and browser launches went through `run-heavy.sh` (light commands of §2 ran directly); one browser launch per run covering all its URLs and widths; related runs named test files, not whole test directories.
2. **Own role only** — the agent ran only the tests and UI checks §1 gives it.
3. **No polling** — no `sleep` loops (waiting for a service to answer included: use `up --wait` or the profile's `app_start`), `pgrep` waits or waits on another agent's process; queued commands ran in the foreground or as background tasks with a completion notification. A script the agent writes never signals completion through a marker file (`*.done`) that something then waits for: the script itself runs as one background task and the harness reports when it ends. Forbidden shapes, for the leader too, include `for i in $(seq …); do …; sleep`, `until grep … ; do sleep`, `timeout N bash -c 'until …'`, `while ! test -f …`, a Monitor or second background task watching the first, and re-reading a background task's output file in a loop: run the test or build in the foreground (through `run-heavy.sh`), or start it in the background and end the turn until its completion notification resumes you.
4. **Suite once** — no full-suite run (unit, integration or e2e target) per task or fix round; at sign-off one full run, flaky failures rerun per file.
5. **Cleanup** — every browser, context, tab, `lightpanda serve`, dev server, watcher and emulator started was stopped before reporting.
6. **No audits in a build task** — the developer swept only the screens and states its task changed (plus every renderer of a changed shared component); wider audits were a planned UI design task.
7. **Lightest tool** — API data was read with `curl`/`jq`, rendered DOM or text with `lightpanda fetch` when installed, and a browser launched only for layout or screenshots; no defect was concluded from Lightpanda alone.
8. **Few turns** — reads, edits and test runs were batched (several files per read command, independent calls in one turn, one `Write` per new file, one pass per edited file, tests after a group of changes); no long runs of one-line reads or edits. Files are edited with the Edit tool (all changes to one file in one pass); a substitution across many files uses `perl -pi -e`; a change across several files can be one unified diff applied with `git apply`; a `python3` script is used only when the change needs logic (parsing JSON, generating data), never a `python3 -` heredoc that re-types old and new text, a `node -e` that writes files, a script that opens project files for writing, or one `sed -i` over several files (the guard hook denies these to agents); an existing file is never re-typed whole; the notes say which edit methods the task used, and more than a few `python3 -` heredoc edits are recorded in the ledger as `COST-8`. The guard hook denies an agent a `python3 -` heredoc that writes files with `.replace(` or `re.sub(`. One round stays under ~120 turns: changes to one file are made in one edit, small edits across files go into one `perl -pi -e` or `git apply`, and checks run once after a group of edits, not after each.
9. **Nothing left running** — the final report states that no background task, server, watcher or browser of this agent is still running.
10. **Related set complete** — besides the tests that import the changed files, the related set includes test files that mention a changed file by name or path (a test that reads a script's text, a snapshot, a manifest check), found with `$TEAM_BIN/rule-checks.sh related-tests <task id>` (every test file of the repository that imports or names a changed file, not only the feature's test folder); the notes show its output, and a fix round runs it again on the round's files. A task that deletes or renames a file, directory, option, route, setting or palette also greps the tests and guard lists for the old name and updates or removes every hit in the same task.
11. **e2e per spec** — when the profile has no `test (e2e, one spec)` command (the project's e2e entry cannot take one spec), the task ran no e2e at all and said so; e2e then runs only at sign-off until an `env` task adds the parameter.
12. **Small requests batched** (leader) — small requests in the same file area that arrive within about 10 minutes of each other, or sit in the queue together, were planned as one task with one review and one commit, not one task each (each task costs a brief, a review, a commit and a report).

13. **Scripts in the workspace** — throwaway scripts, specs and probes live under `$TEAM_WS/qa-artifacts/<task>/`; Playwright is imported by absolute path from the profile's `playwright_dir` (`import { chromium } from '<PLAYWRIGHT_DIR>/node_modules/playwright/index.mjs'`), never taken from an `npx` cache; no resource (tool, font, image, SDK, framework source) is found by searching the disk — paths come from the brief and the profile (`playwright_dir`, `framework_src`), and a missing one is reported to the leader; nothing is written into `$TEAM_TOOLS`.
14. **Waiting on CI and deploys** — CI checks, deploy rollouts and other remote waits run as a background task that ends when the state is final (`gh pr checks <n> --watch` in the background, or one poll at the expected time), never in the foreground of a turn; the leader keeps dispatching and answering meanwhile.
15. **Goldens once** — golden and snapshot files were regenerated once per task (once per fix round when it changes rendering), after the code was final; a golden failure before that was read from its diff image, not regenerated to look. Regenerating is not approval: the changed images are listed and compared by the reviewer (`COMPACT-13`).
16. **Small output in context** — test, build, analyze and golden runs write their full output to a log under `$TEAM_WS/qa-artifacts/<task>/`; the agent reads only the summary line and the failing tests from it (`tail -n 30`, `grep -E -A 15 'FAIL|Error|\[E\]'`), never the whole log, and never prints large generated or binary-backed files (generated keys, lockfiles, golden lists, `.png`). An agent that reaches ~300k tokens writes its notes in full at once (`HANDOVER` ready), so a replacement costs one brief instead of a lost round.
17. **Generated images are regenerated, never merged** — a merge or sync that conflicts in golden or snapshot images is resolved by running the golden update once on the conflicted test files after the code conflicts are settled, never file by file; a worktree task regenerates its goldens once after its last sync with the main branch, not after every sync; golden images are not edited or chosen by hand.
18. **Stop a doomed full run** — a full-suite run whose first failures are all of the environment class (missing table, unknown database, connection refused, missing extension) is stopped once the class is clear, not run to the end; after the `env` fix only the failed files run again, and a second full run happens only when code shared by the suite (test harness, bootstrap, schema) changed since the first. The profile records the measured duration of each full suite (`full_minutes:` on its command line), and the brief sets `AI_DEV_TEAM_TIMEOUT` to about 1.5× that value for the run, so a suite longer than the default is not stopped half-way or rerun with a guessed timeout. A run with many failures that share one assertion pattern and touch nothing in the diff (a language, clock or locale mismatch right after a container restart) has its failed files run once more after the stack check before an `env` task opens; only failures that reproduce become that task.
19. **One check set** — the measurements a task's qc makes (widths × text scales × themes × content variants, the states of the changed screens) live in one script under `$TEAM_WS/qa-artifacts/<task>/` that the developer can run; a fix round or quick pass runs that script before `DONE` and reports it red before the fix and green after, so qc's re-check confirms instead of discovering. The first developer covers the same matrix in its own tests (`COMPACT-11`, `COMPACT-12`).
20. **Cheapest re-check** — a re-check of named cases uses the cheapest evidence that decides them: for Flutter and native screens a widget-test render at that size, scale and theme saved as an image, not a new web or device build; for web screens the existing build when the round did not change the bundle; one build per fix round is shared by every qc check of that round. A full sweep runs only on the task's first qc and at sign-off.
