## Option A: centered card with compact stats strip
Layout: card (rounded `╭╮╰╯`, comment colour) centred horizontally and vertically. 120x40: 78x22; 80x24: 72x20; border padding 1 + 1 space. Rows inside: title (name+version left, branch + file count right), root, blank, SYSTEM rule, row1 `CPU spark + %` | `RAM bar + used/total + %`, row2 `SWP bar + %` | `LOAD x y z  up T`, (120 only) row3 per-core mini bars | `vr-ide cpu% rss`, blank, START rule + keys in 2 columns (4+2 rows, key column 12), blank, RECENT rule + 5 files (dir part dim). Columns split at half of inner width.
40x12 fallback order: per-core row (gone at 80) -> recent 5 -> 3 -> 1 -> card border (gone at 40) -> SYSTEM/START/RECENT headers -> swap, load, uptime, vr-ide figures (strip keeps CPU spark+% and RAM bar+%) -> keys 6 -> 4 (go to file, palette, explorer, quit). The vr-ide own CPU/RSS is only visible at 120.
Pros: calm, most "professional" look, small footprint, reads fine at 80. Cons: border costs 4 rows and 4 cols (against the minimal/density taste); monitor is a small strip so numbers are cramped; vr-ide own figures hidden at 80.

## Option B: two-column dashboard
Layout: left column width 58 (120) / 38 (80), `│` divider in line colour full height, right column the rest, 2-cell padding. Left: name+version, root, `branch · N files`, START rule + all 6 keys (one per row), RECENT rule + 5 (3 at 80). Right: SYSTEM rule; 120: `CPU 37%  60 s`, 6-row block graph of 60 s history (orange where >= 60), 8 per-core horizontal bars in 2 columns with %, RAM and SWP bars with `used/total GiB` and %, LOAD + uptime right-aligned, VR-IDE rule (purple) with own CPU sparkline and RSS bar. 80: CPU spark + %, one row of per-core mini bars, RAM, SWP, LOAD, UP, VR-IDE `cpu rss` line.
40x12 fallback order: right column goes first, reduced to two lines (CPU spark+%, RAM bar+%); divider, recent, headers, uptime/load/swap/self, per-core all gone; keys 6 -> 4.
Pros: the only option where the monitor is a real dashboard (history graph, per-core, own process); keys all visible; best use of 120 columns. Cons: most render code (two columns, graph); at 80 the right column is only 40 wide so it is dense; left column sparse at 120x40.

## Option C: nvim-dashboard style, bottom monitor bar
Layout: 120x40: 5-row block logo `vr-ide` (pink/purple/cyan per letter) centred, tagline row (`version · root · branch · files`, `·` in comment), blank, menu block 40 wide centred (label left, key cyan right-aligned, 6 rows), blank, `Recent` (orange) + 5 files; whole block centred in the area above the monitor. Bottom monitor = 3 rows pinned above the status bar: `─` rule, row 1 `CPU spark % │ RAM bar used/total % │ SWP %`, row 2 `LOAD │ UP │ CORES mini │ vr-ide cpu rss`. 80x24: logo shrinks to a spaced wordmark `v r - i d e`, menu 36 wide, recent 3, monitor still 3 rows.
40x12 fallback order: logo -> wordmark, tagline, recent, rule and row 2 (load, uptime, cores, self, swap) all go; menu 6 -> 4; monitor stays as 2 rows (CPU spark+%, RAM bar+%).
Pros: familiar, scannable, monitor always at the same place, scales best (the bar is the first thing kept); the user's menu keys read like a launcher. Cons: the logo is decoration that costs 6 rows (against design_taste; dropped below 40 rows); the monitor is a thin strip, no history graph or per-core detail, and row 2 is dense at 80; empty bands left and right of the centred menu.

## Recommendation: B
It answers the request "monitor CPU, RAM..." best (history graph, per-core, RAM/swap, load, uptime and vr-ide's own CPU/RSS all visible at 120, and still all the numbers at 80), has no decoration cost, fits the minimal/density taste, and its degrade path is simple (drop the right column down to two lines). If the user wants calmer and smaller, A; C if they prefer the nvim launcher feel. Open for the implement step: per-core and own-process history need a bounded ring buffer (60 samples) in the sampler; Welcome key fallback question from the leader is unchanged.
