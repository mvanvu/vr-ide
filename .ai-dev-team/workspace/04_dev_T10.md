## Repro / root cause
- `flock` locks belong to the **open file description**, not to the descriptor. Every fork (any thread: an agent/terminal PTY via portable-pty `pre_exec`, a `Command`) copies the whole fd table, so the child shares the lock's open file until it execs. The fds are O_CLOEXEC, so no child keeps it past exec.
- Every lock holder released by **closing** its fd only: `session::Keeper.lock` (File), `accounts::AccountLock`, `accounts::IndexLock`, and `remove`'s own exclusive fd. A child forked just before the close keeps the lock alive until its exec. Under load that window outlasts `take_lock`'s 10 × 10 ms retry (session → "Another vr-ide --session window…", so the panel test's last save is skipped) and `remove` has no retry at all (account test).
- Probe evidence: at the failing `remove` the only fd on `.work.lock` left in the test process was remove's own (no lock); the lock was free 2.178 µs later, and no live process had the file open → the holder was a transient forked copy (pre-exec).
- Exec'd children: the probe listed every child (dash, cat, install) at the failure, all `holds_lock_file=false`. No lock fd leaks past exec: std `OpenOptions` sets O_CLOEXEC; accounts.rs opens with explicit `OFlags::CLOEXEC`; portable-pty also closes fds > 2 in pre_exec. So the brief's missing-O_CLOEXEC hypothesis is **not** the cause; the cause is close-instead-of-unlock, the same one-line cause for the session lock and the T8 account/index locks.

## Fix (product, real defect)
Unlock explicitly before the descriptor closes, so the lock is gone for every copy of the open file at once:
- `crates/vr-ide/src/ai/accounts.rs`: `fn unlock(&OwnedFd)` (`flock(LOCK_UN)`); `impl Drop` for `AccountLock` and `IndexLock`; `remove` wraps its exclusive fd in `AccountLock` so it unlocks too. The `#[allow(dead_code)]` on the fields went (Drop reads them).
- `crates/vr-ide/src/session.rs`: `impl Drop for Keeper` → `File::unlock()`; `take_lock` comment updated: the 10 × 10 ms retry stays only for a window that ended without dropping its keeper (killed / exit → kernel close, child forked at that moment). Retry count unchanged; lock semantics unchanged (LOCK_EX non-blocking, 0600, O_NOFOLLOW, owner/regular-file checks, 0700 dir: SEC-6 untouched).
- Not loosened: no test oracle, retry count or lock mode changed.

### Judged points
- LOCK_UN per holder: correct. `flock` locks belong to the open file description; every holder opens its own (`hold`, `remove`, `lock_index`, `take_lock` each `open`; no `try_clone`/`dup` anywhere in the crate), so LOCK_UN frees only that window's lock, plus the forked-child copies of that same description (the intent). Another window's shared hold is a separate description and is untouched: `remove_is_refused_while_another_window_holds_the_account` ("still one holder" after `drop(held)`) passes with the fix (ran it).
- `remove`: wrapping the exclusive fd in `AccountLock` makes every exit path (early `Err("not an account folder")`, `?` on the delete) unlock; the explicit `drop(lock)` after unlinking the lock file keeps the old order.
- Panic/drop: `Drop::drop` runs during unwinding, so a panicking window unlocks too; an aborted/killed process falls back to the kernel close and the unchanged 10 x 10 ms retry.
- Oracle: retry count, LOCK_EX/LOCK_SH non-blocking modes, 0600/O_NOFOLLOW/CLOEXEC/owner checks and 0700 dir unchanged. Red log shows both new tests failing on HEAD for the right reason; green re-run here: 3 passed.

### Findings
[minor, pre-existing, not introduced] crates/vr-ide/src/session.rs:461 — queued save can land after the lock is released
Scenario: quit while the state disk hangs > QUIT_WAIT (5 s) → `save_on_quit` gives up, `Keeper` drops (unlock; before this diff the field drop closed it at the same point), the detached `vr-session` thread still holds a `Msg::Save`; if a new `--session` window takes the lock before this process exits, that window's `remove_stale_temps` may delete the temp (old write fails, harmless) or the old rename lands after the new window restored/saved → the file holds the old window's tabs until the new window's next change. Window = Keeper drop to process exit (exit kills the thread); rename is atomic, no torn file.
Fix (separate task if wanted): move the lock `File` into the writer thread and unlock after `for msg in rx` ends (Keeper drop = drop `tx`), so the lock is never released with a write pending.

[minor] crates/vr-ide/src/session_tests.rs:477 — 2 s pre-exec pause is longer than needed
Scenario: the paused child copies every fd of the whole test process (other parallel tests' pipe write ends, PTY fds) for 2 s, delaying their EOF/exit waits by up to 2 s under the parallel suite; adds 2 s to each of the two tests.
Fix: 300–500 ms is enough (must only exceed the 100 ms retry for the session test; `remove` has no retry).

Out of scope (pre-existing T8, uncertain/low): `hold` stats the folder and opens the lock file before taking LOCK_SH, outside the index lock; a `remove` interleaving between open and flock can delete the folder and unlink the lock, then `hold` succeeds on the unlinked inode → a session starts on a removed account. Not touched by this diff; worth a separate look (re-check the folder after the shared lock is taken).

### Judged
- Finding 1 (late write after unlock): fixed. `Msg::Hold(lock)` is the first message on the channel, so the writer owns the lock before any `Save`; it unlocks only after `for msg in rx` ends (all senders gone = keeper dropped), then drops `end`. If the write hangs past `Keeper::drop`'s 1 s, the lock stays with the writer until the write ends or the process exits (kernel release) — no other window can take the session in between, so a late rename can no longer overwrite another window's file. `send` failure after spawn is unreachable (rx alive); the `unreachable!` arm is sound.
- Writer cannot start: `Err(lock)` hands the `File` back; keeper keeps it, writes inline, `Drop` unlocks — same as before. `saves()` = writer or lock, correct for both.
- Writer panics: `held` closes on unwind (kernel release, covered by the 10 x 10 ms retry), `end` drops so `Keeper::drop` does not wait; later `send`s fail silently, as before the task. `write_file`/`set` have no panicking path, so not reachable in practice.
- Hung write at quit: extra 1 s only after `save_on_quit` already waited QUIT_WAIT (5 s); the terminal is restored before (`event_loop.rs` restores it first), so the user only sees the prompt return 1 s later on a hung state folder. Normal quit: the queue is empty after the flushed quit save, the thread ends at once, `drop` returns immediately. Acceptable. `Keeper` is assigned once at startup (`session.rs:245`), so the wait never runs on the UI loop.
- Finding 2: pause 400 ms in both tests (> 100 ms retry); red-400ms.log shows both still fail with unlock disabled.
- Finding 3: after LOCK_SH, `hold` compares fstat(fd) with statat(`.name.lock`, NOFOLLOW) on st_dev+st_ino and re-checks the folder. A successful LOCK_SH means either remove has not taken LOCK_EX yet (it will then fail) or remove finished (lock unlinked or replaced → inode mismatch; folder gone) → refused, and the dropped `AccountLock` unlocks. Inode reuse impossible while our fd is open. Not a loosened check: only adds a refusal.
- Test-only hooks: `Msg::Pause` and its match arm, `pause_writer_for_tests`, `queue_save_for_tests`, `BEFORE_HOLD_LOCK` and its call are all `#[cfg(test)]`; unreachable in release.
- Oracle: retry count, flock modes, SEC-6 flags unchanged; new tests red on old behaviour (red-qp1.log), green here: 5 passed (forked_child x2, a_quit_window_keeps_the_lock, a_hold_racing, remove_is_refused_while_another_window).

Note, not a finding: a hold whose `statat` passes just before a removal completes recreates an empty 0600 `accounts/.<name>.lock` (O_CREAT) before being refused; harmless and pre-existing.
